## Слайд 2. Постановка проблемы

**Что написать (буллеты):**
- Мультиагентные системы на базе LLM всё чаще решают задачи разработки ПО (план → код → ревью).
- В реальности вход редко идеален: требования **неполны**, содержат **шум**, бывают **противоречивыми**.
- Неизвестно, **насколько сильно деградирует результат** MAS при таких искажениях и какие искажения критичнее.

**Что вставить:** простая схема «грязный вход → MAS → ?» (можно нарисовать стрелками) или диаграмма конвейера из README (mermaid).

**Речь:** «Проблема в том, что MAS обычно тестируют на чистых данных, а устойчивость к искажённому входу системно не измеряют».

## Слайд 3. Актуальность

**Что написать:**

## Слайд 5. Обзор литературы и аналогичных решений

**Что написать (таблица/колонки):**
- **MAS на LLM:** оркестрация ролей (architect/coder/reviewer), AutoGen, MetaGPT, CrewAI, ChatDev.
- **Бенчмарки:** SWE-bench (реальные баги репозиториев), HumanEval, MBPP — но они оценивают *корректность*, а не *устойчивость к искажению входа*.
- **Отказоустойчивость / fault injection:** классика из распределённых систем (внесение сбоев), адаптация к промпт-инжинирингу (perturbation/robustness testing NLP).

**Что вставить:** сравнительная таблица «Решение → что оценивает → пробел».

| Подход | Что оценивает | Пробел |
|---|---|---|
| SWE-bench / HumanEval | корректность решения | чистый вход, нет деградации |
| Robustness NLP (perturbations) | устойчивость модели | одиночная модель, не MAS |
| AutoGen / MetaGPT | оркестрацию ролей | нет метрики устойчивости к шуму входа |

**Речь:** «Существующие бенчмарки меряют корректность на чистых данных; устойчивость MAS именно к искажению постановки задачи системно не покрыта — это и есть наш пробел».

## Слайд 8. Архитектура MAS (объект исследования)

**Что написать:**
- **Архитектор** — строит план решения (без кода).
- **Кодер** — пишет код по плану.
- **Рецензент** — проверяет код, выставляет оценку.
- Последовательный handoff: выход одного агента — вход следующего.

**Что вставить:** схема трёх агентов со стрелками (Architect → Coder → Reviewer).

**Речь:** «Именно многоступенчатость даёт устойчивость: рецензент частично компенсирует искажения».

## Слайд 9. Сценарии отказов (модель угроз)

**Что написать (таблица):**

| Тип | Что моделирует | Реализация |
|---|---|---|
| Неполнота (`incomplete`) | потеря требований | удаление случайных слов |
| Шум (`noise`) | помехи/грязные данные | вставка мусорных символов и текста |
| Противоречие (`contradiction`) | конфликт требований | добавление невыполнимого условия |
| Задержки (delays) | таймауты LLM/сети | наблюдались как `APITimeout`; обработка таймаутов в стенде |

Уровни интенсивности: **low (10%)**, **medium (30%)**, **high (60%)**.

**Что вставить:** таблица + пример «было/стало»:
- *Было:* «Создай класс BankAccount с методами deposit, withdraw, get_balance»
- *Стало (contradiction/high):* «… но не используй циклы (это обязательно)»

**Речь:** «Шум, неполнота и противоречия реализованы как автоматический fault injection; задержки фиксировались как реальный режим отказа сети/LLM».

## Слайд 10. Система метрик

**Что написать:**
- **Качество ответа (0–100%)** = взвешенная сумма: покрытие ключевых слов + полнота агентов (план/код/ревью) + качество кода + содержательность + (для SWE-bench) покрытие предметных терминов.
- **Падение качества:** `loss = (Q_baseline − Q_bug) / Q_baseline × 100%`.
- **Пороги устойчивости:** 🟢 <20% устойчива · 🟡 20–50% средне · 🔴 >50% уязвима.

**Что вставить:** формула крупно + цветовая легенда порогов.

## Слайд 15. Выявленные закономерности (анализ)

**Что написать:**
1. **Многоагентность повышает устойчивость:** ступень «Рецензент» компенсирует шум и противоречия.
2. **Информационные потери критичнее структурного шума:** только неполнота масштабируется с интенсивностью.
3. **Противоречия → не падение, а компромисс:** агенты выбирают выполнимую часть требования (умеренное стабильное падение).
4. **Главный режим реального отказа — задержки/таймауты сети/LLM**, а не семантика.

**Что вставить:** 4 тезиса + маленькое превью heatmap.
